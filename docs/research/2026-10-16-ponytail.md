# Nghiên cứu: `ponytail` (dietrichgebert/ponytail) cho Claude Code

**Xác minh trước tiên:** Đây **đúng là một skill/plugin cho AI coding agent**, cài được vào Claude Code qua `/plugin marketplace add` + `/plugin install`, giống đúng khung `mattpocock/skills` — **không phải** một app/game/thư viện UI không liên quan. Repo có cấu trúc chuẩn plugin Claude Code: `.claude-plugin/plugin.json`, `skills/ponytail/SKILL.md`, `commands/`, `hooks/`, cộng thêm hàng loạt thư mục tương thích agent khác (`.codex-plugin`, `.cursor`, `.windsurf`, `.kiro`, `.qoder`, `.grok-plugin`, `.kimi-plugin`, `.devin-plugin`, `.clinerules`, `.opencode`, `gemini-extension.json`...). Đọc trực tiếp README + `SKILL.md` + `plugin.json` qua `raw.githubusercontent.com` (GitHub web không fetch được do render JS).

---

## 1. Ponytail là gì

- **Tác giả:** Dietrich Gebert (GitHub `DietrichGebert`). Giấy phép MIT. Phát hành song song qua GitHub và npm (`@dietrichgebert/ponytail`).
- **Bản chất:** **một skill duy nhất** (`skills/ponytail/SKILL.md`), không phải một bộ nhiều skill như `mattpocock/skills`. Tên "Ponytail" ẩn dụ "lập trình viên senior lười" (*the lazy senior dev*) — ưu tiên giải pháp nhỏ nhất **giải quyết đủ** việc, không phải nhỏ nhất theo nghĩa ít token nhất.
- **Kích hoạt:** mọi tác vụ viết/sửa/refactor/review code, hoặc khi người dùng nói "be lazy", "simplest solution", "yagni", hoặc phàn nàn code bị over-engineer (thừa thiết kế).
- **Cơ chế cốt lõi — "thang quyết định"** trước khi viết code mới, lấy phương án đầu tiên thỏa được: (1) có cần tồn tại không — bỏ phần không ai yêu cầu; (2) đã có sẵn trong codebase chưa — dùng lại; (3) có trong thư viện chuẩn/nền tảng không; (4) có dependency đã cài sẵn không — dùng, không thêm mới; (5) viết được 1 dòng dễ đọc không; (6) nếu không, viết đoạn tối thiểu.
- **Không cắt:** validation ở ranh giới tin cậy, xử lý lỗi chống mất dữ liệu, bảo mật, accessibility, và mọi thứ người dùng đã yêu cầu rõ. Logic rẽ nhánh/liên quan tiền-bảo mật phải có test nhỏ kèm theo.
- **Quy ước riêng:** comment `shortcut: <giới hạn>, <khi nào cần nâng cấp>` khi biết trước giải pháp có hạn chế — để sau này gom lại bằng `/ponytail-debt`.
- **3 mức:** `lite` (làm đúng yêu cầu + gợi ý 1 dòng phương án nhỏ hơn), `full` (mặc định, áp đầy đủ quy tắc), `ultra` (như full + phản biện luôn cả phần yêu cầu thiếu lý do thực tế).

## 2. Các thành phần cụ thể

| Lệnh/thành phần | Chức năng |
|---|---|
| `/ponytail [lite\|full\|ultra\|off]` | Đổi mức độ hoặc tắt |
| `/ponytail band [on\|off]` | Chỉ Claude Code: ẩn/hiện thanh "band" phía trên ô nhập |
| `/ponytail-review` | Review diff hiện tại: lỗi, bảo mật, tải thực tế (không giả định), thiếu test, phần có thể cắt |
| `/ponytail-audit` | Quét toàn bộ repo, sắp xếp theo mức độ quan trọng |
| `/ponytail-debt` | Gom các comment `shortcut:` thành 1 sổ nợ kỹ thuật |
| `/ponytail-gain` | Hiện bảng số liệu tác động (dựa trên benchmark của tác giả) |
| `/ponytail-help` | Tóm tắt các lệnh |
| **Band (thanh trạng thái, Claude Code ≥ 2.1.290)** | Hiển thị chi phí, token, thời gian agent chạy, tỷ lệ tái sử dụng code sẵn có, trạng thái test sau thay đổi cuối. Nút "Board" mở trang cục bộ tổng hợp các phiên làm việc (`~/.config/ponytail/band/`). Không chạy trong VS Code chat panel, cloud session, hay `claude -p`. |
| **Ledger** | Mặc định bật: ghi 1 dòng CSV/tác vụ (chi phí, lượt, thời gian, token, mức tái sử dụng, test) vào máy cục bộ. |
| **Webhook (tùy chọn, mặc định tắt)** | Có thể gửi JSON tới 1 URL HTTPS riêng sau mỗi lượt; token lưu trong keychain hệ thống, không lưu file/repo. Mặc định rỗng — README ghi rõ "không gì rời khỏi máy" khi không cấu hình. |

**Benchmark tác giả công bố** (39 tác vụ, Opus 5.5, 5 lần/tác vụ, có/không skill): giảm ~53% số dòng code, 41% thời gian, 26% chi phí, 45% token; 98% logic rủi ro có test kèm (không skill: 68%); 30/30 lần đạt trên 6 tác vụ bảo mật test. **Đây là số liệu do tác giả tự công bố trên repo của chính họ, chưa có bên thứ ba kiểm chứng độc lập — chỉ nên coi là tín hiệu định hướng, không phải con số tuyệt đối áp dụng y nguyên cho PiClass.**

## 3. So sánh với bộ skill PiClass đang dùng

Đã đọc trực tiếp `SKILL.md` thật đang cài trên máy (`superpowers` 7.0.0, plugin `engineering` của `claude-plugins-official`) để so sánh chính xác, không đoán.

| Ponytail | Tương đương đã có | Đánh giá |
|---|---|---|
| Triết lý "minimal code, YAGNI" + thang quyết định | `superpowers:test-driven-development` — bước GREEN đã có ví dụ xấu gắn nhãn "YAGNI" ngay trong skill, nguyên tắc "minimal code to pass, không thêm tính năng/refactor ngoài test" | **Trùng lặp đáng kể về tinh thần.** Khác biệt: TDD chỉ áp triết lý này **trong lúc viết code có test trước** (bước GREEN); Ponytail áp **cho mọi tác vụ code**, kể cả việc không đi qua vòng TDD hình thức (sửa config, viết script nhỏ, chọn thư viện) — và có hẳn 1 "thang" 6 bước cụ thể hơn, dễ agent theo hơn 1 nguyên tắc chung. |
| `/ponytail-review` | `superpowers:requesting-code-review`/`receiving-code-review` | **Khác cơ chế, không hoàn toàn trùng.** Superpowers dispatch 1 subagent review riêng (không nhiễu context, có SHA trước/sau cụ thể); `/ponytail-review` là agent tự review diff hiện tại trong cùng session — nhẹ hơn, nhanh hơn, nhưng kém khách quan hơn (không phải "con mắt thứ hai" độc lập). Hai cái bổ trợ nhau: dùng `/ponytail-review` cho kiểm tra nhanh tại chỗ, giữ `requesting-code-review` cho review chính thức trước merge. |
| `/ponytail-debt` | `engineering:tech-debt` (plugin `engineering` đã cài) | **Không trùng, bổ sung hẹp.** `tech-debt` là khung phân loại + chấm điểm ưu tiên (Impact/Risk/Effort) cho **toàn bộ codebase**, chạy khi được yêu cầu "audit tech debt". `/ponytail-debt` chỉ gom đúng các comment `shortcut:` mà **chính Ponytail đã để lại** lúc viết code — hẹp hơn nhiều, nhưng có lợi thế là nợ kỹ thuật được đánh dấu **ngay lúc tạo ra**, không phải suy luận lại sau. |
| `/ponytail-audit` | Không có tương đương trực tiếp đã cài (gần nhất là `mattpocock:improve-codebase-architecture`, chưa cài) | **Bổ sung thật**, nếu dùng. |
| Band (dashboard cost/token/time/reuse/test) | Không có tương đương nào trong `superpowers` hay `engineering` | **Bổ sung giá trị thật, riêng biệt.** Đây là tính năng không trùng với bất kỳ skill nào user đang có — theo dõi chi phí AI theo tác vụ, hữu ích cho một founder 1 người cần biết đang "đốt" bao nhiêu chi phí Claude Code mỗi phiên. |

**Không có skill nào của Ponytail đụng tới `ui-ux-pro-max`/`frontend-design`** — Ponytail chỉ nói về code logic, không có quy tắc UI/thiết kế, nên không chồng chéo với track thiết kế của PiClass.

## 4. Đánh giá & khuyến nghị cho PiClass

**Khuyến nghị: nên cài, dùng ở mức `full` (mặc định), giữ band bật.** Lý do ngắn gọn:

1. PiClass đang ở giai đoạn code BE nhiều module liên tiếp (Step 9) — rủi ro thực tế không phải "thiếu kỷ luật TDD" (đã có `superpowers`), mà là **over-engineering ở những việc KHÔNG đi qua vòng TDD hình thức** (viết migration, config, script, chọn thư viện, sửa nhỏ). Ponytail phủ đúng khoảng trống này nhờ "thang quyết định" áp dụng toàn thời gian, không chỉ lúc code có test.
2. Band dashboard cho biết chi phí/thời gian AI theo tác vụ — giá trị thực tế cho một người vừa code vừa theo dõi ngân sách, mà hiện PiClass chưa có công cụ nào làm việc này.
3. Không xung đột với `superpowers`/`engineering`/`ui-ux-pro-max` đang dùng — Ponytail chỉ là 1 lớp triết lý viết code, chạy song song, không giành quyền kiểm soát quy trình (brainstorm→plan→TDD→review vẫn giữ nguyên).

**Lưu ý khi dùng để tránh xung đột hành vi agent:**
- Vì cả `superpowers:test-driven-development` và Ponytail đều có khái niệm "minimal code"/YAGNI, agent có thể nhắc lại 2 lần trong 1 câu trả lời — không gây hại, chỉ dư chữ. Không cần tắt skill nào.
- `/ponytail-review` không thay thế được `requesting-code-review` (dispatch subagent độc lập) cho các PR lớn/merge module — vẫn giữ quy trình review chính thức hiện tại của PiClass cho các mốc merge quan trọng.
- Nếu chỉ muốn thử nhẹ trước, có thể bắt đầu ở mức `lite` (gợi ý 1 dòng, không áp đặt) rồi nâng lên `full` sau khi thấy hợp.

**Không khuyến nghị dùng ngay:** `/ponytail-audit` toàn repo — tương tự lưu ý đã ghi ở report `mattpocock-skills`, nên để dành chạy định kỳ (ví dụ sau mỗi 1-2 nhóm module BE xong) thay vì chạy ngay, tránh ngập thông tin khi codebase còn đang biến động nhanh.

## 5. Ví dụ áp dụng cụ thể vào PiClass

- Khi viết 1 Form Request validate dữ liệu Laravel cho module mới: Ponytail sẽ chặn việc tự thêm 1 `config()` tùy biến hay 1 lớp wrapper validation riêng nếu Laravel Rule có sẵn đã đủ — đúng kiểu lỗi "thêm abstraction không ai yêu cầu" mà reviewer từng phải bắt tay ở các module trước.
- Sau khi code xong 1 nhánh nhỏ (không qua TDD đầy đủ, ví dụ sửa 1 Eloquent scope), gõ `/ponytail-review` ngay tại chỗ để agent tự rà lỗi/bảo mật/thiếu test trước khi commit — nhanh hơn dispatch subagent review cho việc nhỏ.
- Cuối mỗi tuần hoặc sau khi xong 1 module, gõ `/ponytail-debt` để liệt kê toàn bộ `shortcut:` đã ghi trong tuần đó — đưa vào `docs/progress.md` phần "Minor deferred" thay vì tự nhớ/tự rà tay như hiện tại.
- Dùng band để theo dõi chi phí Claude Code theo module — nếu 1 module BE tốn bất thường nhiều token/chi phí so với các module trước, đó là tín hiệu nên dừng lại xem lại cách giao task (quá rộng, thiếu spec rõ) trước khi làm module tiếp theo.

## 6. Hướng dẫn cài đặt (Claude Code)

Theo README, chạy 2 lệnh slash trong Claude Code:

```
/plugin marketplace add DietrichGebert/ponytail
/plugin install ponytail@ponytail
```

- Sau cài, mặc định ở mức `full`. Đổi mức bằng `/ponytail lite` / `/ponytail ultra` / `/ponytail off`.
- Band cần Claude Code ≥ 2.1.290; tắt riêng band (giữ skill) bằng `/ponytail band off` nếu không muốn thanh trạng thái hiện trên UI nhưng vẫn muốn giữ triết lý code tối giản.
- Cài cho agent khác (Codex, Cursor...) xem chi tiết trong `INSTALL.md` của repo — không cần cho PiClass vì stack hiện tại chạy Claude Code.
- Theo CLAUDE.md của PiClass: skill cài scope local, không commit qua git — nên nếu quyết định cài, nên bổ sung 2 lệnh trên vào `docs/setup/claude-skills-setup.md` (mục mới) để máy khác/người khác chạy lại được, giống cách đã làm với `superpowers`/`ui-ux-pro-max`.

## 7. Lưu ý rủi ro/quyền riêng tư

- **Mặc định an toàn:** `webhookUrl` rỗng, `ledger` chỉ ghi CSV cục bộ trên máy — không có dữ liệu nào rời máy nếu không tự cấu hình webhook. Đây là claim từ README chính thức của tác giả, đã đọc trực tiếp `plugin.json`, không phải suy đoán.
- Nếu về sau có bật `webhookUrl` để gửi số liệu task lên 1 dashboard riêng, cân nhắc tắt `sendNames` (mặc định bật) nếu tên tác vụ/prompt đầu tiên có thể chứa thông tin nhạy cảm của PiClass (ví dụ nhắc tên học sinh/giáo viên thật trong 1 prompt) — nhưng với cách dùng hiện tại (không cấu hình webhook), rủi ro này không phát sinh.
- Số liệu benchmark (53% ít code hơn, 41% nhanh hơn...) là **tự công bố, không có bên thứ ba kiểm chứng** — chỉ nên dùng làm kỳ vọng định hướng, không nên trích dẫn như số liệu đã được xác thực khi báo cáo lại cho người khác.
