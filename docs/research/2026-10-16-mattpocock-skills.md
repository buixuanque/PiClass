# Nghiên cứu: bộ skills `mattpocock/skills` cho Claude Code

Nguồn: repo GitHub [`mattpocock/skills`](https://github.com/mattpocock/skills) — đọc trực tiếp README và các `SKILL.md` qua `raw.githubusercontent.com` (vì GitHub web render bằng JS nên WebFetch trên `github.com` chỉ lấy được danh sách thư mục, không lấy được nội dung đầy đủ). Đã đọc 20/20 `SKILL.md` nhóm `engineering/` và 7/7 nhóm `productivity/` (27 skill), cộng README và `.claude-plugin/marketplace.json`.

**Lưu ý kỹ thuật:** công cụ WebFetch mà agent nghiên cứu dùng tóm tắt lại nội dung thay vì trích dẫn nguyên văn (nó tự áp giới hạn trích dẫn trực tiếp từ trang web). Vì vậy các mô tả skill dưới đây là tóm tắt trung thực theo nội dung đọc được, không phải copy nguyên văn `SKILL.md`. Một số chi tiết kỹ thuật rất nhỏ (ví dụ cờ `disable-model-invocation: true` — tức "model không tự gọi skill này, chỉ chạy khi người dùng gõ lệnh `/ten-skill`" — của một vài skill) không xác nhận được 100% cho từng skill, nên phần "model-invoked vs user-invoked" ở mục 6 chỉ nên coi là tham khảo, không phải khẳng định tuyệt đối.

## 1. Tổng quan bộ skill

- **Tác giả:** Matt Pocock — người sáng lập [Total TypeScript](https://totaltypescript.com) / aihero.dev, nổi tiếng trong cộng đồng TypeScript. Tên repo trên marketplace: **"Skills For Real Engineers"**.
- **Mục đích chung:** bộ quy trình (không phải thư viện code) để các coding agent (Claude Code, Codex, GitHub Copilot, Gemini CLI...) làm phần mềm "thật" thay vì "vibe coding" (code theo cảm tính, không kiểm chứng). README nêu rõ 4 vấn đề mà bộ skill này giải quyết:
  1. Agent hiểu sai ý → phỏng vấn kỹ trước khi làm (`/grill-me`, `/grill-with-docs`).
  2. Agent viết dài dòng, không nhất quán thuật ngữ → xây "ngôn ngữ chung" qua `GLOSSARY.md` + ADR (Architecture Decision Record — tài liệu ghi lại một quyết định kiến trúc quan trọng và lý do).
  3. Code chạy không đúng → vòng lặp TDD (`/tdd`) và quy trình debug có kỷ luật (`/diagnosing-bugs`).
  4. Codebase rối dần theo thời gian → review kiến trúc định kỳ (`/improve-codebase-architecture`, `/to-spec`).
- **Khác gì với "superpowers" mà user đang dùng:** cả hai đều là bộ skill *quy trình phát triển phần mềm* (brainstorm → spec → TDD → review → merge), không riêng cho TypeScript — các skill đọc được đều generic, không có skill nào yêu cầu cú pháp TypeScript cụ thể. Sự khác biệt nằm ở **đơn vị tổ chức công việc**:
  - `superpowers` tổ chức công việc quanh **file plan local trong repo** (`docs/archive/superpowers/plans/`), thực thi tuần tự/song song trong 1 session hoặc qua subagent, không bắt buộc có issue tracker thật.
  - `mattpocock/skills` tổ chức công việc quanh **issue tracker thật** (GitHub Issues, GitLab, Linear, hoặc file Markdown giả lập trong `.scratch/`) với một hệ nhãn triage cố định (`needs-triage`, `ready-for-agent`, `wontfix`...) và một đồ thị ticket có quan hệ "blocking" (chặn lẫn nhau) — thiết kế cho việc nhiều ticket chạy song song qua nhiều subagent/nhiều phiên/nhiều người, kể cả quản lý bug report từ người dùng ngoài.
  - Bộ này cũng có 2 nhóm skill mà superpowers không có tương đương rõ: **productivity** (soạn câu hỏi gửi người khác, bàn giao phiên làm việc, học một kỹ năng mới qua nhiều buổi...) và **wizard** (script bash dẫn người dùng qua các bước chỉ con người làm được, như bấm vào AWS Console).
- **Không nhắm riêng TypeScript:** đúng như tên "Total TypeScript" gợi ý ban đầu, nhưng nội dung đọc được hoàn toàn là quy trình ngôn ngữ-trung lập (git, test, review, kiến trúc, tài liệu) — áp dụng được cho Laravel/Next.js của PiClass không có rào cản kỹ thuật nào. Cái không áp dụng được không phải vì "chỉ cho TypeScript" mà vì **trùng chức năng với skill user đã có**, hoặc **đòi hỏi hạ tầng user chưa dùng** (issue tracker thật cho công việc hàng ngày).

### Nhóm `engineering/` (20 skill)

| Skill | Mục đích | Quy trình chính |
|---|---|---|

| **grill-with-docs** | Phỏng vấn gắt gao để làm rõ kế hoạch/thiết kế, vừa phỏng vấn vừa ghi `GLOSSARY.md`/ADR ngay trong lúc nói chuyện. | Gọi lồng 2 skill con: `grilling` (hỏi theo vòng) + `domain-modeling` (chốt thuật ngữ). |

| **domain-modeling** | Thống nhất thuật ngữ nghiệp vụ (domain), duy trì `GLOSSARY.md`. | Đối chiếu thuật ngữ mới với glossary hiện có → nếu mâu thuẫn, nêu ngay → kiểm tra bằng ví dụ cụ thể → cập nhật glossary → chỉ đề xuất ghi ADR khi quyết định khó đảo ngược + dễ gây hiểu lầm + là một đánh đổi thật. |
| **codebase-design** | Bộ từ vựng thiết kế "module sâu" (deep module): interface nhỏ, hành vi phong phú bên trong, dễ test qua chính interface đó. | Đưa ra khái niệm: seam (ranh giới interface), leverage/locality (lợi ích cho người gọi/người bảo trì), và "deletion test" — thử tưởng tượng xóa module này: nếu độ phức tạp biến mất thì nó chỉ là lớp trung gian vô dụng, nếu độ phức tạp "mọc lại" ở nhiều nơi gọi thì module đang có giá trị thật. |
| **improve-codebase-architecture** | Quét định kỳ codebase để tìm chỗ nên "làm sâu" module (refactor có lợi), không phải sửa bug. | Ưu tiên code thay đổi gần đây → dùng sub-agent rà soát + áp "deletion test" → xuất 1 file HTML độc lập (Tailwind + Mermaid qua CDN) liệt kê từng ứng viên kèm mức khuyến nghị (Strong/Worth exploring/Speculative) → người dùng chọn ứng viên → vào vòng phỏng vấn sâu (grilling) về ràng buộc/đánh đổi → cập nhật glossary/ADR. |
| **to-spec** | Biến một cuộc trò chuyện đã bàn xong thành 1 spec, đăng lên issue tracker. | Khám phá codebase theo glossary/ADR → phác thảo các "seam" cần test, xác nhận lại → viết spec theo khung cố định (Problem Statement, Solution, User Stories đánh số theo "As a... I want... so that...", Implementation Decisions, Testing Decisions, Out of Scope) → đăng lên tracker, gắn nhãn `ready-for-agent`. |
| **to-tickets** | Chia 1 spec/kế hoạch thành nhiều ticket dạng "tracer bullet" (lát cắt dọc, chạy xuyên hết các tầng: schema→API→UI→test, demo được độc lập) có khai báo quan hệ chặn nhau (blocking edges). | Khám phá codebase → phác thảo ticket (ngoại lệ: refactor diện rộng dùng mô hình "expand–contract") → duyệt với người dùng → đăng lên tracker theo đúng thứ tự phụ thuộc (không đóng/sửa issue cha). |
| **wayfinder** | Lập kế hoạch cho một khối việc quá lớn/mơ hồ để làm trong 1 phiên — tạo "bản đồ" (map issue) và giải quyết các "ticket quyết định" (research/prototype/grilling/task) lần lượt tới khi rõ đường đi. | Lập bản đồ (Destination, Decisions so far, Not yet specified, Out of scope) → giải quyết từng ticket trên "frontier" (ticket không bị chặn) → cập nhật bản đồ sau mỗi ticket. Nguyên tắc: *lập kế hoạch, không thực thi* — sản phẩm là quyết định, không phải code. |
| **implement** | Thực hiện 1 việc dựa trên spec/ticket cụ thể. | Lấy ticket từ tracker → dùng `tdd` tại các điểm tích hợp đã thống nhất → chạy typecheck/test liên tục → review bằng `code-review` → commit vào branch hiện tại. |
| **implement-spec** | Triển khai **toàn bộ** 1 spec bằng nhiều subagent chạy song song (mỗi ticket 1 subagent trong 1 git worktree riêng), rồi gộp lại. | Tạo integration branch → mỗi ticket giao cho 1 subagent (TDD, merge tip integration branch về mình trước khi báo xong) → 1 merger subagent gộp vào integration branch → khi hết ticket, chạy `code-review` trên integration branch, giao lỗi lại cho subagent sửa → mở PR/đóng ticket → dọn worktree. |
| **tdd** | Vòng lặp Test-Driven Development có nguyên tắc chặt: test phải kiểm hành vi qua interface công khai (không test chi tiết cài đặt nội bộ), kỳ vọng phải lấy từ nguồn độc lập (tránh test "tự chứng minh mình đúng"), đi theo lát dọc (1 test – 1 cài đặt tối thiểu – lặp lại), không viết hết test rồi mới viết code. | Thống nhất "seam" cần test trước với người dùng → viết test thất bại → viết code tối thiểu cho qua → lặp. Refactor không nằm trong vòng lặp, thuộc giai đoạn review riêng. |
| **diagnosing-bugs** | Quy trình debug có kỷ luật 6 pha cho bug khó/hồi quy hiệu năng. | (1) Xây **vòng phản hồi** 1 lệnh cho tín hiệu đạt/không đạt tái hiện đúng lỗi, xác định (deterministic), chạy nhanh, không cần người; (2) tái hiện + thu gọn input tới mức tối thiểu còn giữ được lỗi; (3) liệt kê 3–5 giả thuyết kiểm chứng được; (4) đặt "probe" (log có tiền tố `[DEBUG-xxxx]` để dễ xoá, mỗi lần chỉ đổi 1 biến); (5) sửa lỗi + viết test hồi quy từ repro đã thu gọn; (6) dọn dẹp (xoá log debug, xoá prototype tạm, ghi giả thuyết đúng vào commit/PR). Luôn che giấu bí mật (`<REDACTED>`) trước khi hiển thị log/lệnh. |
| **research** | Giao việc đọc tài liệu/nghiên cứu cho 1 agent chạy nền, lưu kết quả vào 1 file Markdown trong repo, có trích dẫn nguồn cho mỗi khẳng định, ưu tiên nguồn chính thức hơn bài tổng hợp. | Tra cứu → ghi file → lưu đúng thư mục theo quy ước repo (hoặc tự chọn và báo đường dẫn). |
| **code-review** | Review 2 chiều độc lập: **Standards** (có đúng coding convention của repo + 12 code smell của Fowler không) và **Spec** (có đúng yêu cầu issue/spec gốc không, có thiếu/thừa scope không). | Lấy diff theo 1 điểm cố định (branch/commit) → tìm nguồn spec (issue liên kết trong commit message, file spec...) và nguồn chuẩn mực (CODING_STANDARDS.md...) → chạy 2 sub-agent riêng (không nhiễu context nhau) → trình bày 2 báo cáo cạnh nhau, không gộp/không xếp hạng ai "thắng". |
| **pr** | Template viết nội dung Pull Request, phát triển từ skill `show-me` của Dex Horthy (Humanlayer). | 3 phần: **Summary** (minh hoạ nhỏ nhất đủ rõ: pseudocode, call tree, sơ đồ Mermaid, diff, cây thư mục...), **Evidence** (bằng chứng hoạt động đúng — ưu tiên screenshot, sau đó là kết quả test trước/sau), **Merge Danger** (rủi ro: "cửa 1 chiều" hay "2 chiều" — có đảo ngược được không — và "blast radius" — phạm vi ảnh hưởng). |
| **retro** | Rút kinh nghiệm sau 1 phiên code — nhưng cải tiến **môi trường của agent** (tài liệu, lint/test tự động, coding standards, quyền truy cập thông tin), không phải review code. | Đọc log phiên → tìm ứng viên cải tiến theo nhóm: navigation (khó tìm file), automated checks (thiếu/để lọt lint-test), coding standards, tool economy, no-ops (chỉ dẫn vô dụng), information access (thiếu quyền đọc log/service) → trình bày theo mức độ nghiêm trọng. |
| **prototype** | Dựng 1 prototype dùng-một-lần để trả lời câu hỏi thiết kế trước khi code thật (không phải MVP, bỏ hết phần hoàn thiện: không test, không xử lý lỗi). | 2 nhánh: **Logic/state machine** → 1 file HTML độc lập có nút thao tác tự do để đưa state machine qua các case khó suy luận trên giấy; **UI** → nhiều biến thể UI khác hẳn nhau trên cùng 1 route, chuyển bằng tham số URL. Khi chốt, đưa quyết định vào code thật, lưu prototype trên 1 branch tạm (không phải main), ghi lại câu hỏi đã được giải đáp. |
| **wizard** | Viết script bash hướng dẫn người dùng qua các bước **chỉ con người làm được** (bấm AWS Console, thiết lập CI secret, chạy migration một lần...), mở đúng URL, chỉ rõ cần bấm gì, tự lưu giá trị vào `.env`/GitHub secrets. | Xác định phạm vi (đọc `.env.example`, README, workflow CI để biết cần giá trị gì) → lập hành trình từng bước cụ thể (không tự bịa UI nếu không chắc) → viết script dựa trên `template.sh` dùng sẵn các helper (`stage`, `ask_secret`, `write_env`, `confirm`...) → kiểm tra tĩnh (`bash -n`, `shellcheck`), không chạy thử tự động vì cần tương tác người. |

## 4. Khuyến nghị skill nên dùng

**Nên cài plugin (vì có ít nhất vài skill giá trị thật, chi phí cài gần như 0 — các skill không dùng cũng không ảnh hưởng vì phần lớn chỉ chạy khi gõ `/ten-skill`):**

1. **`improve-codebase-architecture`** — chạy định kỳ (gợi ý: sau mỗi 1-2 nhóm module BE xong, hoặc cuối Step 9) trên `piclass-api/` để tìm chỗ nên "làm sâu" module, đặc biệt hữu ích vì `docs/progress.md` đang tích lũy khá nhiều "Minor deferred" qua các module — đây đúng là lúc dọn kiến trúc có hệ thống thay vì để trôi.
2. **`prototype`** — dùng cho cả 2 việc: (a) kiểm chứng logic/state machine phức tạp ở BE trước khi viết spec/TDD (ví dụ status machine của `Assessment`/`Attempt` đã từng bị reviewer tìm ra lỗi guard thiếu ở Module 3 — prototype trước có thể bắt lỗi này sớm hơn, rẻ hơn); (b) khám phá nhiều biến thể UI khác nhau trước khi chốt `MASTER.md` design system (đang làm lại qua Claude Design, chưa có token chính thức — đúng giai đoạn cần).
3. **`retro`** — chạy sau mỗi lần merge PR lớn (xong 1 module BE, hoặc sau sự cố như vụ merge nhầm base branch đã xảy ra ở Module 3) để hệ thống hóa việc rút kinh nghiệm thành cải tiến `CLAUDE.md`/CI-check, thay vì chỉ ghi tay vào `MEMORY.md` như hiện tại.
4. **`wizard`** — dành riêng cho giai đoạn deploy EC2 (còn mở ở `ARCH-12`, CI/CD chưa chọn công cụ) — viết 1 script dẫn đường cho các bước tay: tạo EC2, security group, Let's Encrypt, GitHub Actions secrets.
5. **`pr`** (nhẹ, đi kèm plugin, không tốn công cài riêng) — dùng template PR (Summary + Evidence + Merge Danger) cho các PR quan trọng (merge module BE/FE lớn), thay thế nội dung PR sơ sài hiện tại.

**Để dành, cài khi tới lúc (không cần ngay):**
- **`triage`** + `setup-matt-pocock-skills` — bật khi PiClass launch thật và bắt đầu nhận bug report qua GitHub Issues từ người dùng ngoài (giáo viên/học sinh thật).

**Không cần cài / bỏ qua vì trùng lặp:** `tdd`, `implement`, `implement-spec`, `to-spec`, `to-tickets`, `diagnosing-bugs`, `code-review`, `grill-with-docs`, `grilling`, `domain-modeling`, `codebase-design`, `wayfinder`, `research`, `handoff`, `ask-matt` (router chỉ cần nếu dùng cả bộ).

**Niche, dùng tùy hứng, không ảnh hưởng quyết định chính:** `grill-me`, `to-questionnaire`, `wait-what`, `teach`, `writing-for-agents`.

**Kết luận một hướng rõ ràng:** cài plugin (chi phí gần bằng 0), nhưng **chỉ tích cực dùng 5 skill ở tier 1** (`improve-codebase-architecture`, `prototype`, `retro`, `wizard`, `pr`) ngay trong giai đoạn hiện tại; giữ `triage` cho giai đoạn hậu-launch; bỏ qua toàn bộ phần còn lại vì PiClass đã có cách làm tương đương (hoặc tốt hơn, vì gắn liền với `docs/requirements`, `docs/architecture/open-decisions.md` cụ thể của dự án) qua `superpowers`.

## 5. Ví dụ áp dụng cụ thể vào PiClass

- **`/improve-codebase-architecture`** — sau khi cả BE 5 module đã merge `main` (đúng tình trạng hiện tại), chạy skill này trên `piclass-api/`. Kỳ vọng: nhận 1 file HTML mở trên máy, liệt kê ví dụ như "logic tính điểm `AutoGrader`/`ResultCalculator` (Module 4) có đang bị gọi rải rác từ nhiều controller không, hay đã gọn trong 1 service" — nếu không dùng skill, việc dọn kiến trúc chỉ xảy ra khi reviewer tình cờ phát hiện lúc review PR (như đã xảy ra ở Module 3/4), bị động hơn.
- **`/prototype`** (nhánh Logic) — trước khi viết spec cho một business rule có state machine phức tạp (ví dụ nếu sau này cần sửa lại luồng `close/reopen/cancel` của `Assessment` — đúng khu vực đã bị reviewer tìm ra 3 lỗi Critical ở Module 3), dựng 1 file HTML mô phỏng state machine, bấm thử mọi trạng thái trước khi vào TDD thật. Kỳ vọng khác biệt: bắt được case quên guard ("có thể republish khi đang closed") ngay ở bước thiết kế, rẻ hơn nhiều so với bắt ở final review sau khi đã code+test xong.
- **`/prototype`** (nhánh UI) — khi bắt đầu Plan 1b/2b (FE Auth + User Management, đang nợ theo `docs/progress.md`), trước khi chốt `MASTER.md`, dựng 2-3 biến thể UI màn hình login/dashboard khác hẳn nhau trên cùng route Next.js, chuyển bằng query param, để founder xem và chọn hướng — rồi mới đưa cho `ui-ux-pro-max`/Claude Design chốt chi tiết.
- **`/retro`** — ngay sau khi merge PR #11 (retrofit Module 4 Audit+Notification, vừa xong), chạy retro cho phiên đó. Kỳ vọng: skill tự đề xuất "nên có CI check chặn merge nhầm base branch" dưới dạng rule cụ thể (git hook hoặc GitHub branch protection), hệ thống hóa đúng bài học mà user đã tự ghi tay vào `MEMORY.md` (`feedback_git_fetch_before_branch.md`) sau sự cố PR #2/#3.
- **`/wizard`** — khi tới lúc giải quyết `ARCH-12` (file retention) và chọn CI/CD, dùng wizard để sinh 1 script dẫn: mở AWS Console tạo EC2 + security group → mở GitHub repo Settings → Secrets tạo `SSH_KEY`/`DB_PASSWORD` → chạy Let's Encrypt lần đầu trên EC2. Kỳ vọng: giảm sai sót tay (ví dụ quên set 1 secret) so với làm theo checklist tĩnh của `engineering:deploy-checklist`.
- **`/pr`** — áp dụng cho PR module FE đầu tiên (Plan 1b): phần Summary dùng sơ đồ Mermaid luồng Login→SetRoleContext, phần Evidence là screenshot trước/sau UI + kết quả Playwright test, phần Merge Danger ghi rõ đây là "cửa 2 chiều" (dễ rollback) hay có phá vỡ gì với cookie-session Sanctum đang chạy (ARCH-05) không.
- **`/triage`** (để dành) — sau khi PiClass launch, một giáo viên report "không chấm được bài qua `Attempt` reissue" qua GitHub Issue → `/triage` sẽ tự đối chiếu với `.out-of-scope/` (có từng từ chối yêu cầu tương tự chưa), tái hiện theo bước giáo viên mô tả, rồi gắn nhãn `ready-for-agent` kèm "agent brief" để Claude Code code fix ngay — thay vì user tự đọc report rồi viết lại thành yêu cầu.

## 6. Hướng dẫn cài đặt

**Cách chính thức cho Claude Code (xác nhận từ README):**

```bash
claude plugin install mattpocock-skills@claude-plugins-official
```

- Cú pháp: `claude plugin install <tên-plugin>@<marketplace>`. `mattpocock-skills` là plugin, `claude-plugins-official` là marketplace chứa nó (theo `.claude-plugin/marketplace.json` của repo, package tên `mattpocock` do Matt Pocock/aihero.dev sở hữu, danh mục "engineering").
- README không nói rõ `claude-plugins-official` có cần `claude plugin marketplace add` trước hay đã có sẵn mặc định trong Claude Code — đây là điểm **chưa xác minh chắc chắn**, nên nếu lệnh trên báo lỗi "marketplace not found", thử thêm bước `claude plugin marketplace add <url-hoặc-tên>` trước (tương tự cách user hẳn đã từng add vào máy cho `superpowers`/`engineering`, có thể xem lại cách add cũ trong `docs/setup/claude-skills-setup.md`).
- Sau khi cài, mở 1 session Claude Code trong `piclass-api/` (hoặc repo tương ứng) và chạy **1 lần/repo**:
  ```
  /setup-matt-pocock-skills
  ```
  Lệnh này hỏi 3 phần: issue tracker dùng gì (nếu không dùng GitHub Issues cho mục đích này, có thể chọn "Markdown cục bộ trong `.scratch/`" để không ảnh hưởng gì tới GitHub thật), nhãn triage (chỉ cần nếu dùng `/triage`), và vị trí `GLOSSARY.md`/ADR (nên bỏ qua/chọn tối giản nếu không có ý định dùng `domain-modeling`/`codebase-design`/`to-spec`).
  - Vì PiClass gồm nhiều repo riêng (`piclass-api`, `piclass-infra`, `piclass-web`/docs), cần chạy `/setup-matt-pocock-skills` **riêng cho từng repo** nếu muốn dùng skill phụ thuộc tracker ở đó — nhưng theo khuyến nghị mục 4, có thể **bỏ qua hẳn bước này** nếu chỉ dùng 5 skill tier 1 (`improve-codebase-architecture`, `prototype`, `retro`, `wizard`, `pr`), vì các skill này không bắt buộc có issue tracker đã cấu hình (một vài có thể hỏi và chấp nhận câu trả lời "không dùng tracker, chỉ in ra kết quả tại chỗ").
- **Cảnh báo quan trọng từ README:** không cài đồng thời cả plugin này **và** bản copy qua `skills.sh` (công cụ copy skill thủ công vào project, cho các agent không hỗ trợ plugin) — nếu làm cả hai, mỗi skill sẽ xuất hiện 2 lần, gây nhiễu. Chỉ cài 1 trong 2 cách. Với Claude Code, nên dùng cách `claude plugin install` ở trên, không cần `skills.sh`.
- **Rủi ro cần lưu ý khi cài xong:** vài skill có thể tự động kích hoạt theo câu nói (model-invoked) mà không cần gõ `/ten-skill`, ví dụ `diagnosing-bugs` có thể tự bật khi gõ "debug cái này giúp tôi" — đúng câu cũng hay dùng để gọi `superpowers:systematic-debugging`. Nếu thấy Claude Code có dấu hiệu chạy nhầm skill (của mattpocock thay vì superpowers) cho các việc đã có skill tương đương, nên tắt các skill trùng lặp không dùng (`tdd`, `diagnosing-bugs`, `code-review`, `grilling`, `domain-modeling`, `to-spec`, `to-tickets`, `implement`, `implement-spec`) qua cấu hình plugin của Claude Code (`claude plugin` có lệnh enable/disable từng skill con — cần tra thêm cú pháp chính xác lúc cài thật, chưa xác minh được qua tài liệu đọc được).
